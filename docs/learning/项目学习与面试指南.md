# 电商智能数据分析助手：学习与面试指南

这份文档面向零基础学习者。它会随项目阶段持续更新：每完成一个功能，就补充“它解决什么问题、你需要会什么、如何运行、面试如何讲”。

## 1. 先用一句话介绍项目

> 项目最终目标是构建基于 LLM Agent 的电商智能数据分析助手；当前已完成 Phase 1 数据导入、Phase 2 指标分析、Phase 3 安全 NL2SQL、Phase 4 Agent 编排、Phase 5 本地知识检索、Phase 6 FastAPI 接口、Phase 7 Streamlit 操作界面、Phase 8 数据库报告闭环、Phase 9 用户行为漏斗与 Phase 10 自动识别与报告建议。

## 2. 项目最终工作流

```text
上传 Excel / CSV
  → 字段自动匹配（当前 CLI 遇到歧义直接拒绝，后续 Streamlit 支持人工确认）
  → 数据清洗、质量审计、MySQL 入库
  → 用户自然语言提问
  → LangGraph Agent 制定任务计划
  → 安全 SQL 查询 + Pandas 指标计算
  → 异常检测 + RAG 知识检索
  → Streamlit 图表与文字版报告
```

你需要记住：LLM **不负责计算业务数值**，它只负责理解问题、选择工具、解释已经计算出的结果。GMV、ROI、转化率等都由 SQL 或 Pandas 按固定公式计算。

## 4. Phase 1：必须掌握的知识

### 4.1 从零运行并验收一次导入

项目统一使用 Python 3.10。先安装依赖，复制环境变量模板并按本机 MySQL 修改 `.env` 中的 `DATABASE_URL`：

```powershell
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

全新数据库只执行最新版 `sql/001_schema.sql`。PowerShell 示例：

```powershell
Get-Content -Raw sql/001_schema.sql | mysql -u root -p ecommerce_db
```

已经执行过早期 Phase 1 DDL 的旧库不能靠重跑 `CREATE TABLE IF NOT EXISTS` 获得新增列。应先备份，并同时清理支付/退款的重复 ID 与重复自然键数据，再一次性执行 `sql/002_phase1_integrity_upgrade.sql`；该迁移补充 `error_code`、`age`、七个 `is_outlier` 和支付/退款双重唯一约束。

Excel 工作簿可以只包含部分标准工作表。工作表名称必须是 `user_info`、`order_info` 等标准表名；未知工作表会忽略，已识别的工作表会在同一个事务中导入：

```powershell
python -m backend.scripts.import_data --file data/phase1.xlsx
```

Excel 不接受 `--table`，传入该参数会明确拒绝，避免用户以为只导入一张表而实际导入整个工作簿。

读取时 CSV 字段和 Excel 文本单元格按文本保真，因此 `00123` 和高精度金额不会先被 Pandas 推断成整数或浮点数。Excel 数值单元格只能保留工作簿本身的数值语义；需要前导零的 ID 必须在源文件中保存为文本单元格。

CSV 一个文件只对应一张表，因此每次必须用 `--table` 明确标准表。多文件要逐个执行命令，例如：

```powershell
python -m backend.scripts.import_data --file data/users.csv --table user_info
python -m backend.scripts.import_data --file data/orders.csv --table order_info
```

每次命令都会输出 JSON 导入报告。可以用下面三组小案例验收清洗与缺表报告：

- 年龄 `[20, 缺失, 40, 150]` 会清洗为 `[20, 30, 40, 30]`：缺失值和越界值都使用本批次有效年龄均值 30 填充，并在质量摘要的 `filled.age` 中记录 2。
- 无法解析日期的记录会被跳过，并计入质量摘要；金额小于等于 0 的记录会被跳过，并计入质量摘要。两类记录都不会写入业务表，计入 `skipped` 和 `invalid`，而不是静默修正或参与后续分析。
- Phase 1 只报告 `missing_tables`，不执行指标/图表降级。后续分析层应据此禁用依赖缺失表的能力，例如缺少 `traffic_visit` 时禁用 UV、PV 和转化率，缺少 `ads_info` 或 `ad_attribution` 时禁用 ROI 与归因分析。

数据库中的 `quality_summary` 会持久化 `missing_tables`、每表 `unmapped_source_columns`、按字段和原因拆分的 `reasons`、填充/跳过/去重计数，以及当前文件可判定的 `relationship_anomalies`。失败批次还保存稳定 `error_code`；内部数据库异常不会原样输出到 CLI。

导入流程始终复用 `FileImportAdapter` 读取文件、`suggest_mapping` 建议字段映射、`clean_frame` 执行确定性清洗，再由 `ImportService` 在单个事务中写入和审计。命令返回非零退出码或 JSON 中出现 `error` 时，应先修正字段、表名或数据库配置，再重新导入。

### 4.2 CSV 与 Excel 的区别

- CSV 是纯文本表格，一个文件通常对应一张表；简单、通用，但不包含多个工作表。
- Excel `.xlsx` 可以在一个工作簿中放多张工作表，适合一次导入多类业务数据。
- 本项目允许 Excel 工作表不齐全，也允许连续上传多个 CSV。Phase 1 会报告缺少哪些标准表；指标和图表的实际降级由后续分析层实现。

### 4.3 为什么要做字段映射

不同公司字段名称常不同，例如“订单编号”“订单ID”都可能表示 `order_id`。系统会按中英文别名自动建议映射；当前 CLI 只接受唯一匹配，遇到缺失或歧义映射会直接拒绝导入。后续 Streamlit 再提供人工确认和映射模板保存能力。这样数据库内部始终使用统一字段名，后续 SQL 与指标计算不必为每种文件格式重写。

### 4.4 为什么要数据清洗

原始业务文件经常含有缺失、重复、格式错误和异常值。若直接分析，结论会失真。

项目约定：

- 年龄有效范围为 1–100 且必须是整数；缺失、越界或 `20.5` 等小数年龄按无效年龄处理，用当前批次有效整数年龄均值填充并审计。
- 无法解析日期、未来订单日期、金额或价格小于等于 0 的记录不进入分析，并写入质量报告。
- 只有 `order_time` 会拒绝未来日期；其他日期字段只要求可解析，未来广告排期等数据不会被误删。
- 当前批内去重只按与 DDL 一致的完整业务键保留首条，不比较同键内容冲突；其余重复记录计入 `deduplicated`。数据库中已存在相同业务键时，整个新批次以 `cross_batch_duplicate` 拒绝并留下失败审计。
- 极高金额并不直接删除：它可能是真实大额订单。系统标记为待核验的业务异常，再决定是否在报告中展示。

### 4.5 MySQL 数据建模

本项目不是只有一张“订单表”。为了正确计算营收、退款、流量和 ROI，需要拆分事实表：

- `order_info`：用户什么时候下单、订单来自哪个渠道。
- `order_item`：订单买了什么、买了几件。
- `payment_info`：订单支付时间、金额、方式和状态。
- `refund_info`：订单退款时间、金额、原因和状态。
- `traffic_visit`：访问会话、用户、访问时间、页面和来源渠道，用于后续 UV/PV。
- `ads_info` 与 `ad_attribution`：投放消耗、曝光点击和归因成交，用于 ROI。

这样拆分的好处是：一个订单可以有多个商品、多个退款记录；流量和投放也不应混在订单表中。

数据库还包含两张管理表：`import_batch` 保存每次导入的文件、状态、字段映射和数据质量摘要，便于追溯；`metric_config` 保存阈值、统计天数和 ROI 回溯周期等可配置参数。所有业务表都记录 `import_batch_id`，因此出现异常指标时可以追溯到具体导入批次。

金额、价格和成本在 Python 中先用 `Decimal` 和 `ROUND_HALF_UP` 量化到两位小数，并限制为 `0.01` 到 `9999999999999999.99`，再以字符串参数交给 MySQL `DECIMAL(18,2)`，避免提前进入二进制浮点路径；业务事件时间使用 `DATETIME`。

### 4.6 本项目如何清洗数据

数据清洗不是“把看起来奇怪的数据都删掉”。项目把规则分为三类：

- **可修复的数据**：存在有效年龄时，年龄缺失或越界值使用本批次均值填充并按半入规则保存为整数。全批次无有效年龄时保持为空，`filled["age"] = 0`；纯缺失不增加 `invalid`，不可解析和越界值都会按原因增加。
- **不可用的数据**：无法解析的日期、未来订单日期、金额或价格小于等于 0 的记录不会参与分析，并会被统计到跳过原因中。
- **可能有业务价值的数据**：特别高的金额不会删除，而是使用 IQR 方法标记为异常。它可能是录入错误，也可能是大客户订单，需要在最终报告中提示运营人员核验。

去重也必须谨慎。订单明细不能只按订单号去重，因为同一订单可以购买多个商品；广告归因也不能只按订单号去重，因为同一成交可能对应不同广告触点。项目会按每张表完整的业务唯一键（必要时包含多个字段）识别真正重复的数据。

### 4.7 文件导入工作流如何保证可靠

CSV 一次对应一张标准业务表；Excel 可以包含多张标准工作表，未知工作表会被忽略。`IMPORT_BATCH_SIZE` 仅控制数据库查询和写入分块，包括集合式查重、父键查询和 `executemany`，不代表流式文件读取。

Phase 1 MVP 会把文件整表加载到内存后再映射和清洗，因此只适合内存可容纳的文件；超大文件需在后续阶段增加 CSV 流式读取和跨块清洗状态，当前能力不作此承诺。

字段映射失败发生在创建批次前，因此不产生失败批次。映射和清洗成功后，系统先独立提交 `processing` 审计，再开启业务事务执行跨批次重复检测、分块写入所有业务表并更新为 `completed`。如果任一写入失败，业务事务整体回滚；随后独立更新审计为 `failed`，因此不会留下“半份数据”，也不会丢失失败记录。

人工确认与映射模板保存都属于后续 Streamlit；当前 CLI 只拒绝歧义并输出 JSON 错误。

命令行成功时向 stdout 输出报告 JSON，失败时向 stderr 输出带稳定错误码的 JSON。多工作表批次使用固定标签保存于短字段，已处理标准表可由 `quality_summary.tables` 得到，缺失标准表保存在 `missing_tables`；未知工作表不进入审计。

## 5. 高频面试问题与参考答案

### Q1：这个项目解决了什么问题？

**参考答案：** 电商运营数据通常分散在不同 Excel 或 CSV 文件中，字段名不统一，分析依赖人工 SQL 和经验判断。这个项目先把数据标准化，再让用户用自然语言获取查询、指标、异常和运营建议，降低数据分析门槛，同时保留 SQL、指标公式和数据质量的可追溯性。

### Q2：为什么不让 LLM 直接计算 GMV、转化率和 ROI？

**参考答案：** LLM 擅长理解和生成文本，但不适合作为精确、可审计的计算引擎。业务指标必须由固定 SQL/Pandas 公式计算，保证同一数据在报表、预警和归因中得到一致结果。LLM 只负责路由工具、解释结论和生成建议。

### Q3：为什么支持字段映射，而不是要求用户固定模板？

**参考答案：** 真实企业导出的字段命名差异很大。当前 CLI 用自动别名匹配处理唯一候选，遇到缺失或歧义映射就拒绝导入，避免静默错配。后续 Streamlit 将增加人工确认并保存映射模板，兼顾准确性和重复导入效率。

### Q4：年龄缺失为什么用均值填充？有什么风险？

**参考答案：** 年龄是画像辅助字段，有有效年龄时用同批次均值填充可以让聚合分析继续进行，并在 `filled.age` 记录数量；全批次没有有效年龄时则保留为空。风险是均值会削弱真实分布，因此后续报告应在填充比例过高时提示画像结论可信度下降。对订单金额等业务事实字段不能这样填充，因为会伪造营收。

### Q5：为什么高金额订单不直接删除？

**参考答案：** 高金额可能是录入错误，也可能是企业客户的大额真实订单。直接删除会低估 GMV，因此采用 IQR 标记而不是删除；如果它显著影响经营结论，就在报告中作为待核验的业务异常展示。

### Q6：如何保证 SQL 安全？

**参考答案：** SQL Agent 生成的语句必须经过白名单校验：只允许单条 `SELECT` 或 `WITH ... SELECT`，仅访问标准表；拒绝多语句、注释绕过以及 `INSERT`、`UPDATE`、`DELETE`、`DROP` 等危险关键词。数据库连接还会使用只读账户。

### Q7：数据清洗时，为什么不能简单地按订单号去重？

**参考答案：** 因为订单与订单商品明细是一对多关系。同一个订单可能购买多个不同商品；如果只按订单号去重，会误删合法商品明细，导致商品销量、件单价和品类贡献度计算错误。因此去重要基于完整业务键，例如订单商品明细至少需要“订单号 + 商品号”。

### Q8：为什么金额字段不用 FLOAT？

**参考答案：** `FLOAT` 使用二进制近似表示，小数计算可能产生精度误差。电商金额需要准确到分，因此 MySQL 使用 `DECIMAL(18,2)` 保存金额、价格和成本，SQL/Pandas 计算时也要避免把最终金额口径交给 LLM。

### Q9：`import_batch_id` 有什么价值？

**参考答案：** 它把每条业务数据关联到一次具体导入。出现字段映射错误、清洗比例过高或指标异常时，可以追溯文件、映射配置和质量摘要，也能明确某次导入影响了哪些表，而不必猜测数据来源。

### Q10：多工作表 Excel 导入时，如何避免只写入一部分数据？

**参考答案：** 所有表的字段映射和清洗先在事务外验证；随后先持久化批次审计，再用一个业务事务完成主动查重、所有业务表写入和完成状态。任意一张表失败都会整体回滚业务数据，并在独立事务中把既有审计标成失败，因此既没有半成品数据，也保留失败证据。

### Q11：字段自动映射有哪些风险？

**参考答案：** 一是源字段找不到标准字段，二是一个源字段可能对应多个候选，三是多个源字段可能同时映射同一个目标字段。本项目在数据库写入前检查这三种情况；当前 CLI 直接拒绝含糊映射，后续 Streamlit 再提供人工确认，避免静默丢列或错误覆盖。

### Q12：业务表不完整时，为什么只报告缺表而不拒绝全部数据？

**参考答案：** 不同分析依赖的事实表不同。Phase 1 当前只在 `missing_tables` 中列出缺表，不执行指标降级；后续分析层将据此禁用依赖缺失表的指标。例如缺少访问表时不计算 UV、PV 和转化率，但订单与支付数据仍可支持销售额分析。

## 6.1 已完成：Phase 1 数据基础

目前项目已经完成以下基础能力：

1. **环境配置骨架**：数据库地址和导入批次大小从 `.env` 读取，不写死在代码中；这也是保护账号、密码和 API Key 的常见做法。
2. **字段映射契约**：系统定义了用户、订单、支付、退款、访问、广告归因等十类标准表，并能将“订单编号”“用户ID”“下单时间”“渠道”等不同来源列名映射为统一内部字段。
3. **可审计的数据导入**：支持 Excel 部分工作表与多个 CSV，确定性地完成清洗、去重、事务写入，并记录字段映射、质量摘要和缺失表。

字段映射有一个重要安全规则：只有一个标准字段能匹配时才自动映射；如果一个源列可能对应多个字段，当前 CLI 会停止并拒绝导入。这避免了“看起来能导入、实际字段对应错了”的隐蔽数据问题；人工确认将在后续 Streamlit 中实现。

## 6.2 已完成：Phase 2 指标、异常与报告内核

系统已能在 Pandas 层统一计算 GMV、实际销售额、退款、净销售额、UV/PV、转化、复购、广告 ROI 与商品 Top N；分母为 0 或依赖缺失时明确返回不可计算，不伪造 0。报告仅编排工具输出为指标、图表数据、缺失依赖、质量提示、有效异常和规则化建议；缺表只取消对应图表，其他结果继续输出。

核心口径：统计区间为 `[start, end)`；金额使用 `Decimal`；GMV 按下单金额，实际销售额扣除优惠、满减和运费并剔除全额退款，净销售额再扣成功退款。异动支持日环比、周同比、月环比：5% 起轻微、15% 起显著、超过 30% 严重；IQR/3 Sigma 用于标记时间序列异常，只有严重变化或双证据异常进入“有价值异常”。

**Q：为什么报告层不能重新写 GMV 或 ROI 公式？**
**答：** 报表、预警和归因必须共用同一套计算结果。报告层只做编排，避免同一指标在不同页面因重复实现产生口径漂移。

**Q：缺少流量表时怎样保证报告有用？**
**答：** 依赖按指标隔离：销售数据完整时仍输出销售指标；依赖 `traffic_visit` 的 UV、转化和流量图表明确取消，并在 `missing_dependencies` 中给出缺失名称，方便补数。

**Q：异常为什么不能直接视为数据错误？**
**答：** 大额订单或突增可能是真实业务机会。系统只标记和提示核验，结合导入批次、渠道和运营活动再判断，不在清洗阶段擅自删除。

## 6.3 已完成：Phase 3 安全 NL2SQL 基础

自然语言问题先由兼容 OpenAI 接口的模型生成候选 SQL，再经过本地安全校验才可执行。校验层只允许单条 `SELECT` 或 `WITH ... SELECT`，仅能访问项目白名单业务表；注释、多语句、写操作、未知表和超出最大行数的查询会被拒绝。未写 `LIMIT` 的查询会自动限制为 `NL2SQL_MAX_ROWS`，默认 1000 行。

配置 `.env` 中的 `LLM_BASE_URL`、`LLM_API_KEY` 和 `LLM_MODEL` 后，可执行：

```powershell
python -m backend.scripts.ask_data --question "查询订单数量"
```

数据库账户仍必须使用只读权限。SQL 白名单是应用层防护，数据库权限是第二道防线；两者不能互相替代。

**Q：为什么不能把 LLM 生成的 SQL 直接执行？**

**答：** LLM 输出本质上是不可信输入，可能出现误删、越权查询、多语句拼接或超大结果集。项目将它限制为“候选 SQL”，随后通过语句类型、注释、多语句、表白名单和行数上限校验；最后再由只读数据库账户执行，形成双层防护。

## 6.4 已完成：Phase 4 LangGraph Agent 编排

`EcommerceSupervisor` 使用 LangGraph 的 `StateGraph` 管理状态和节点路由：分析类问题调用既有指标/异常/报告工具；涉及 SQL、原始数据或明细的问题才进入安全查询节点。每一步都会留下 `trace`，例如 `supervisor:analysis → tool:analysis_report`，便于排查任务走向。

Agent 不重新计算 GMV、ROI 等业务指标，也不绕过 Phase 3 的 SQL 校验。未配置 LLM 或只读查询执行器时，SQL 路由返回 `nl2sql_not_configured`，不会尝试连接数据库或执行不受控语句。

**Q：为什么要使用 LangGraph，而不是在一个函数里写很多 if/else？**

**答：** Agent 的任务会逐步增加查询、分析、报告、检索和人工确认等分支。`StateGraph` 将状态、节点与路由条件显式化，每个节点只完成一件事，后续新增 RAG 或人工审核节点时不会把流程控制和业务计算混在一起；同时可保留执行轨迹，方便测试和排错。

## 6.5 已完成：Phase 5 本地知识检索

项目将 `docs/knowledge/` 下的运营 Markdown 按标题切成知识片段。用户询问“GMV 的口径是什么”这类规则问题时，Supervisor 路由到知识检索节点，返回命中的文本和来源文件；例如 `knowledge/电商指标口径.md`。检索只解释业务规则，不读取订单数据、不重新计算指标，也不执行 SQL。

当前版本采用离线、确定性的中文二元词和英文词召回，适合简历演示、单元测试和没有 API Key 的环境。它是 RAG 的检索基础而非语义 Embedding 检索：面对同义改写或大量文档时，后续可替换为 Embedding 与向量索引，但必须继续保留来源引用和“LLM 不参与指标计算”的边界。

**Q：为什么知识库不能替代数据库查询？**

**答：** 知识库回答的是“GMV 如何定义、ROI 如何计算”这类稳定规则；数据库与 Pandas 工具回答的是“本期 GMV 是多少”这类实时事实。前者不应被当作交易数据，后者也不能由 LLM 或文档内容随意改写口径。项目通过独立 Agent 路由将二者分开。

## 6.6 已完成：Phase 6 FastAPI 接口

启动本地接口：

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.app.api:app --reload
```

启动后访问 `http://127.0.0.1:8000/docs` 可在浏览器中测试接口。`GET /health` 检查服务状态；`POST /api/ask` 接收 `{"question":"GMV 的口径是什么？"}` 并调用 Agent；`POST /api/analysis` 接收表数据和统计时间区间，并复用报告内核；`POST /api/imports` 接收 CSV 或 Excel，复用既有字段映射、清洗和事务导入。导入仍需要在 `.env` 配置数据库。

上传文件只在临时目录中处理，完成后删除；文件类型仅接受 `.csv` 和 `.xlsx`。API 不直接拼接 SQL，也不在 HTTP 层重算 GMV、ROI 等指标。

**Q：为什么 API 层要保持“薄”？**

**答：** HTTP 层负责参数校验、状态码和 JSON 序列化；导入、指标计算、SQL 安全校验和 Agent 路由继续由已有服务负责。这样 CLI、后续前端和 API 共用同一套业务规则，避免接口层复制公式产生口径漂移，也更容易进行单元测试。

## 6.7 已完成：Phase 7 Streamlit 操作界面

请打开两个 PowerShell 窗口，并都先进入 `D:\shufen\ecommerce-agent`。第一个窗口启动 API：

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.app.api:app --reload
```

第二个窗口启动界面：

```powershell
.\.venv\Scripts\streamlit.exe run frontend/app.py
```

浏览器会打开 Streamlit 页面。你可以上传 `.xlsx` 或 `.csv`；CSV 必须在页面中选择对应标准表。点击“清洗并导入”后，页面把文件交给 API，再由已有导入服务完成映射、清洗和事务写入。知识问答页可直接输入“GMV 的口径是什么？”并展示引用来源。

当前界面不承诺“上传后直接显示历史分析图表”，因为后端尚未提供从数据库读取并按时间筛选的报告接口；下一阶段会补齐这条读取链路后再接入可视化，避免前端绕过统一指标口径。

**Q：为什么 Streamlit 不直接连接数据库？**

**答：** 前端只负责交互，不应保存数据库账号、执行 SQL 或重复数据清洗逻辑。Streamlit 通过 HTTP 调用 FastAPI；API 再调用经过测试的导入、分析和 Agent 服务。这样凭据、权限与业务规则集中在后端，后续替换为 React 等前端也不会影响核心逻辑。

## 6.8 已完成：Phase 8 数据库报告闭环

先按 Phase 7 的双窗口方式启动 API 与 Streamlit。导入数据后，在“分析看板”选择统计开始和结束日期，再点击“生成报告”。页面请求 `GET /api/reports`；后端从标准业务表只读加载数据，调用与 Phase 2 相同的报告内核，页面展示成交 GMV、实际销售额、净销售额、退款金额、金额柱状图、异常和规则建议。

`/api/reports` 只能读取项目的标准表白名单，不能传入任意表名或 SQL。前端不直连数据库；缺少依赖表时，报告继续输出可计算部分，并提示缺失数据。当前时间区间采用 `[start, end)`：若要看 7 月 1 日到 7 月 31 日，应把结束日期填为 8 月 1 日。

**Q：为什么单独建立只读分析仓储？**

**答：** 导入仓储负责写入、去重和审计；分析仓储只负责读取标准表并规范化时间类型。职责分开后，报告内核仍然只接收 DataFrame，不依赖 Web 或数据库实现，因而 CLI、API 与测试可以复用同一套指标口径；同时白名单能减少任意表访问带来的风险。

## 6.9 已完成：Phase 9 用户行为漏斗

你的 `用户行为分析.csv` 是匿名访客画像与页面标记数据，并非逐条事件日志：它没有用户 ID、事件 ID 或时间。因此不能导入 `behavior_info`，应在 Streamlit 的 CSV 下拉框中选择 `behavior_funnel`。

已有数据库请先执行一次迁移：

```powershell
Get-Content -Raw sql/004_behavior_funnel.sql | mysql -u root -p ecommerce_db
```

再导入 CSV，并进入“用户行为漏斗”页点击“生成漏斗分析”。看板输出匿名访客数、新访客占比、首页→列表页→商品页→支付页→确认页的访客漏斗，以及来源渠道的确认页转化率。页面访问字段按“该访客是否访问过该页面”计数，不把页面浏览次数误当访客数量。

**Q：为什么不把这类文件强行映射为行为事件表？**

**答：** 事件表需要每个事件的唯一标识、事件类型和发生时间，才能计算按日趋势、UV 去重和行为序列。该文件只给出每位匿名访客的聚合页面标记，缺少这些事实；强行补造 ID 或时间会制造虚假数据。独立的漏斗表保留其真实粒度，并能正确支持来源、设备和页面转化分析。

## 6.10 已完成：Phase 10 自动识别与报告建议

上传 CSV 或 Excel 后，默认不用选择标准表：系统将源列名与每类数据的字段契约逐一比较。只有某一候选表的必填字段齐全、没有字段歧义，且它的匹配字段数最高时，才会自动导入；否则返回 `cannot_auto_identify` 或 `ambiguous_table`，不会写入数据库。页面的“手动选择表”仅作为无法自动识别时的后备选项。

导入成功后页面会说明识别出的数据类型及其可支持的报告。例如：`behavior_funnel` 自动展示用户漏斗；`order_info` 提示进入分析看板选择时间区间生成 GMV 报告；`traffic_visit` 提示流量报告；`ads_info` 提示投放报告及归因数据依赖。系统也同时返回数据质量摘要，因此“能导入”不等于“所有指标都可计算”。

若页面提示 `database_unavailable_or_schema_missing`，先确认 `.env` 的 `DATABASE_URL` 使用真实 MySQL 账号，`ecommerce_db` 数据库已创建，并在新数据库执行 `sql/001_schema.sql`；已有旧数据库还需执行新增功能对应的迁移脚本。前端会显示 API 的可读错误信息，不再显示 JSON 解析堆栈。

日常启动可直接执行一键脚本：

```powershell
cd D:\shufen\ecommerce-agent
.\scripts\start_app.ps1
```

它会分别打开 API 与 Streamlit 的终端窗口，并自动打开浏览器。第一次运行若被 PowerShell 阻止，可只对当前窗口执行 `Set-ExecutionPolicy -Scope Process Bypass` 后重试；脚本不会修改系统级执行策略。

**Q：为什么自动识别不用 LLM？**

**答：** 数据表识别决定了清洗规则、数据库字段和指标口径，必须可审计、可复现。项目使用字段别名、必填字段和唯一最高匹配数的确定性规则；LLM 可以解释识别结果，但不能替代这个写入前的结构校验。遇到并列候选时拒绝自动写库，比猜错一张表更安全。
