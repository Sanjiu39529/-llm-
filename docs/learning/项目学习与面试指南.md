# 电商智能数据分析助手：学习与面试指南

这份文档面向零基础学习者。它会随项目阶段持续更新：每完成一个功能，就补充“它解决什么问题、你需要会什么、如何运行、面试如何讲”。

## 1. 先用一句话介绍项目

> 我开发了一个基于 LLM Agent 的电商智能数据分析助手。它支持上传 Excel/CSV 数据，完成字段映射、数据清洗和 MySQL 入库；用户用自然语言提问后，系统通过受控 SQL、指标计算、异常检测和知识检索，生成包含图表与运营建议的分析报告。

## 2. 项目最终工作流

```text
上传 Excel / CSV
  → 字段自动匹配与人工确认
  → 数据清洗、质量审计、MySQL 入库
  → 用户自然语言提问
  → LangGraph Agent 制定任务计划
  → 安全 SQL 查询 + Pandas 指标计算
  → 异常检测 + RAG 知识检索
  → Streamlit 图表与文字版报告
```

你需要记住：LLM **不负责计算业务数值**，它只负责理解问题、选择工具、解释已经计算出的结果。GMV、ROI、转化率等都由 SQL 或 Pandas 按固定公式计算。

## 3. 分阶段学习路线

| 阶段 | 你会学到什么 | 简历中可强调什么 |
|---|---|---|
| Phase 1：数据基础 | Excel/CSV、Pandas、数据清洗、MySQL 建模、数据质量 | 构建可追溯的数据导入链路，兼容不完整文件与不同字段名 |
| Phase 2：指标分析 | SQL 聚合、Pandas、GMV、转化、ROI、异常检测 | 固化统一电商指标口径，避免 LLM 改变计算规则 |
| Phase 3：NL2SQL | Prompt、Schema 注入、SQL 白名单、安全校验 | 实现只读 SQL 防护，防止删除/修改数据 |
| Phase 4：Agent | LangGraph、状态机、工具调用、任务路由 | 使用 Supervisor 编排查询、分析与报告节点 |
| Phase 5：RAG | 文档切分、Embedding、FAISS、召回 | 用业务知识提升解释与建议质量，但不替代事实数据 |
| Phase 6：FastAPI | REST API、Pydantic、错误模型、日志 | 将 Agent 能力封装成可调用后端服务 |
| Phase 7：Streamlit | 文件上传、状态展示、表格、图表 | 完成运营人员可直接使用的分析界面 |

## 4. Phase 1：必须掌握的知识

### 4.1 从零运行并验收一次导入

项目支持 Python 3.11–3.13。先安装依赖，复制环境变量模板并按本机 MySQL 修改 `.env` 中的 `DATABASE_URL`：

```powershell
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

在已经创建好的目标数据库中执行 `sql/001_schema.sql`。PowerShell 示例：

```powershell
Get-Content -Raw sql/001_schema.sql | mysql -u root -p ecommerce_db
```

Excel 工作簿可以只包含部分标准工作表。工作表名称必须是 `user_info`、`order_info` 等标准表名；未知工作表会忽略，已识别的工作表会在同一个事务中导入：

```powershell
python -m backend.scripts.import_data --file data/phase1.xlsx
```

CSV 一个文件只对应一张表，因此每次必须用 `--table` 明确标准表。多文件要逐个执行命令，例如：

```powershell
python -m backend.scripts.import_data --file data/users.csv --table user_info
python -m backend.scripts.import_data --file data/orders.csv --table order_info
```

每次命令都会输出 JSON 导入报告。可以用下面三组小案例验收清洗与部分数据降级：

- 年龄 `[20, 缺失, 40, 150]` 会清洗为 `[20, 30, 40, 30]`：缺失值和越界值都使用本批次有效年龄均值 30 填充，并在质量摘要的 `filled.age` 中记录 2。
- 无法解析日期的记录会被跳过，并计入质量摘要；金额小于等于 0 的记录会被跳过，并计入质量摘要。两类记录都不会写入业务表，计入 `skipped` 和 `invalid`，而不是静默修正或参与后续分析。
- 缺少 `traffic_visit` 时，UV、PV 和转化率分析降级为不可用；缺少 `ads_info` 或 `ad_attribution` 时，广告 ROI 与归因分析不可用。其余已导入表仍可使用，导入报告的 `missing_tables` 会明确列出缺失表，系统不会补造数据。

导入流程始终复用 `FileImportAdapter` 读取文件、`suggest_mapping` 建议字段映射、`clean_frame` 执行确定性清洗，再由 `ImportService` 在单个事务中写入和审计。命令返回非零退出码或 JSON 中出现 `error` 时，应先修正字段、表名或数据库配置，再重新导入。

### 4.2 CSV 与 Excel 的区别

- CSV 是纯文本表格，一个文件通常对应一张表；简单、通用，但不包含多个工作表。
- Excel `.xlsx` 可以在一个工作簿中放多张工作表，适合一次导入多类业务数据。
- 本项目允许 Excel 工作表不齐全，也允许连续上传多个 CSV。缺少数据时，系统只取消依赖该数据的指标和图表，不会伪造结果。

### 4.3 为什么要做字段映射

不同公司字段名称常不同，例如“订单编号”“订单ID”都可能表示 `order_id`。系统会按中英文别名自动建议映射，再让用户确认。这样数据库内部始终使用统一字段名，后续 SQL 与指标计算不必为每种文件格式重写。

### 4.4 为什么要数据清洗

原始业务文件经常含有缺失、重复、格式错误和异常值。若直接分析，结论会失真。

项目约定：

- 年龄有效范围为 1–100；缺失或不在范围内时，用当前批次有效年龄均值填充。
- 无法解析日期、未来订单日期、金额或价格小于等于 0 的记录不进入分析，并写入质量报告。
- 完全重复的业务主键记录去重；同主键但内容冲突时记录冲突。
- 极高金额并不直接删除：它可能是真实大额订单。系统标记为待核验的业务异常，再决定是否在报告中展示。

### 4.5 MySQL 数据建模

本项目不是只有一张“订单表”。为了正确计算营收、退款、流量和 ROI，需要拆分事实表：

- `order_info`：用户什么时候下单、订单来自哪个渠道。
- `order_item`：订单买了什么、买了几件。
- `payment_info`：支付金额、优惠券、满减和运费。
- `refund_info`：退款金额、退款状态、退货数量。
- `traffic_visit`：访客、设备、访问时间和来源渠道，用于 UV/PV。
- `ads_info` 与 `ad_attribution`：投放消耗、曝光点击和归因成交，用于 ROI。

这样拆分的好处是：一个订单可以有多个商品、多个退款记录；流量和投放也不应混在订单表中。

数据库还包含两张管理表：`import_batch` 保存每次导入的文件、状态、字段映射和数据质量摘要，便于追溯；`metric_config` 保存阈值、统计天数和 ROI 回溯周期等可配置参数。所有业务表都记录 `import_batch_id`，因此出现异常指标时可以追溯到具体导入批次。

金额、价格和成本使用 `DECIMAL(18,2)`，避免浮点数计算产生金额误差；业务事件时间使用 `DATETIME`。常用查询字段建立复合索引，例如订单时间与渠道、广告活动与日期，以支持后续指标分析。

### 4.6 本项目如何清洗数据

数据清洗不是“把看起来奇怪的数据都删掉”。项目把规则分为三类：

- **可修复的数据**：年龄缺失、年龄小于 1 或大于 100，会使用本批次有效年龄均值填充；如果没有有效年龄，则保留为空并记录质量问题。
- **不可用的数据**：无法解析的日期、未来订单日期、金额或价格小于等于 0 的记录不会参与分析，并会被统计到跳过原因中。
- **可能有业务价值的数据**：特别高的金额不会删除，而是使用 IQR 方法标记为异常。它可能是录入错误，也可能是大客户订单，需要在最终报告中提示运营人员核验。

去重也必须谨慎。订单明细不能只按订单号去重，因为同一订单可以购买多个商品；广告归因也不能只按订单号去重，因为同一成交可能对应不同广告触点。项目会按每张表完整的业务唯一键（必要时包含多个字段）识别真正重复的数据。

### 4.7 文件导入工作流如何保证可靠

CSV 一次对应一张标准业务表；Excel 可以包含多张标准工作表，未知工作表会被忽略。导入顺序是：读取文件、自动建议字段映射、检查缺失/歧义字段、清洗全部数据、开启数据库事务、创建导入批次、写入所有业务表、更新批次状态。

导入使用一个数据库事务：如果 Excel 的前几张表已经写入，但后一张表失败，整个批次都会回滚，不会留下“半份数据”。字段映射也必须是一对一；例如“用户ID”和“用户编号”同时映射到 `user_id` 时，系统会在清洗和数据库写入前拒绝并提示歧义。

命令行导入成功和失败都输出 JSON，便于未来 FastAPI、Streamlit 或自动任务稳定解析。多工作表批次使用固定标签保存于短字段，完整工作表清单保存在审计 JSON 中，兼顾 MySQL 字段长度和可追溯性。

## 5. 高频面试问题与参考答案

### Q1：这个项目解决了什么问题？

**参考答案：** 电商运营数据通常分散在不同 Excel 或 CSV 文件中，字段名不统一，分析依赖人工 SQL 和经验判断。这个项目先把数据标准化，再让用户用自然语言获取查询、指标、异常和运营建议，降低数据分析门槛，同时保留 SQL、指标公式和数据质量的可追溯性。

### Q2：为什么不让 LLM 直接计算 GMV、转化率和 ROI？

**参考答案：** LLM 擅长理解和生成文本，但不适合作为精确、可审计的计算引擎。业务指标必须由固定 SQL/Pandas 公式计算，保证同一数据在报表、预警和归因中得到一致结果。LLM 只负责路由工具、解释结论和生成建议。

### Q3：为什么支持字段映射，而不是要求用户固定模板？

**参考答案：** 真实企业导出的字段命名差异很大。固定模板会提高使用门槛；自动别名匹配加人工确认可以兼顾效率和准确性。确认后的映射还可以保存为模板，减少重复操作。

### Q4：年龄缺失为什么用均值填充？有什么风险？

**参考答案：** 年龄是画像辅助字段，缺失时用同批次有效年龄均值可以让聚合分析继续进行。风险是均值会削弱真实分布，因此系统必须记录填充比例；若缺失比例过高，报告应提示画像结论可信度下降。对订单金额等业务事实字段不能这样填充，因为会伪造营收。

### Q5：为什么高金额订单不直接删除？

**参考答案：** 高金额可能是录入错误，也可能是企业客户的大额真实订单。直接删除会低估 GMV，因此采用 IQR 标记而不是删除；如果它显著影响经营结论，就在报告中作为待核验的业务异常展示。

### Q6：如何保证 SQL 安全？

**参考答案：** SQL Agent 生成的语句必须经过白名单校验：只允许单条 `SELECT` 或 `WITH ... SELECT`，仅访问标准表；拒绝多语句、注释绕过以及 `INSERT`、`UPDATE`、`DELETE`、`DROP` 等危险关键词。数据库连接还会使用只读账户。

### Q7：数据清洗时，为什么不能简单地按订单号去重？

**参考答案：** 因为订单与订单商品明细是一对多关系。同一个订单可能购买多个不同商品；如果只按订单号去重，会误删合法商品明细，导致商品销量、件单价和品类贡献度计算错误。因此去重要基于完整业务键，例如订单商品明细至少需要“订单号 + 商品号”。

### Q8：为什么高金额要标记而不是直接删除？

**参考答案：** 统计异常不等于脏数据。高金额可能是异常录入，也可能是真实的大额企业采购。系统使用 IQR 标记异常，并让它保留在营收事实中；只有在报告中说明它对 GMV 或趋势的影响，才既避免漏掉重要经营事件，也能提示人工核验。

### Q9：为什么金额字段不用 FLOAT？

**参考答案：** `FLOAT` 使用二进制近似表示，小数计算可能产生精度误差。电商金额需要准确到分，因此 MySQL 使用 `DECIMAL(18,2)` 保存金额、价格和成本，SQL/Pandas 计算时也要避免把最终金额口径交给 LLM。

### Q10：`import_batch_id` 有什么价值？

**参考答案：** 它把每条业务数据关联到一次具体导入。出现字段映射错误、清洗比例过高或指标异常时，可以追溯文件、映射配置和质量摘要，也能明确某次导入影响了哪些表，而不必猜测数据来源。

### Q11：多工作表 Excel 导入时，如何避免只写入一部分数据？

**参考答案：** 所有表的字段映射和清洗先在事务外验证，确认可写后再开启一个数据库事务。批次审计、所有业务表写入和完成状态都处于同一事务；任意一张表失败都会整体回滚，因此不会留下不一致的半成品数据。

### Q12：字段自动映射有哪些风险？

**参考答案：** 一是源字段找不到标准字段，二是一个源字段可能对应多个候选，三是多个源字段可能同时映射同一个目标字段。本项目在数据库写入前检查这三种情况，并把含糊映射交给后续 UI 人工确认，避免静默丢列或错误覆盖。

### Q13：业务表不完整时，系统为什么选择降级而不是拒绝全部数据？

**参考答案：** 不同分析依赖的事实表不同。例如没有访问表就不能可靠计算 UV、PV 和转化率，但订单与支付数据仍可支持销售额分析。导入报告会列出缺失表，分析层再禁用依赖这些表的指标。这样既不伪造数据，也不会因为一个可选表缺失而浪费其他有效数据。

## 6. 本阶段完成后你应能演示什么

完成 Phase 1 后，你应能拿一个字段名不同、工作表不完整的 Excel 或多个 CSV，说明：

1. 系统如何识别文件和工作表；
2. 如何自动匹配“订单编号”等源字段；
3. 数据清洗前后有什么差异；
4. 哪些记录被跳过、填充、去重或标记异常；
5. 为什么缺少某张表会让某些后续图表不可用。

## 6.1 已完成：Phase 1 数据基础

目前项目已经完成以下基础能力：

1. **环境配置骨架**：数据库地址和导入批次大小从 `.env` 读取，不写死在代码中；这也是保护账号、密码和 API Key 的常见做法。
2. **字段映射契约**：系统定义了用户、订单、支付、退款、访问、广告归因等十类标准表，并能将“订单编号”“用户ID”“下单时间”“渠道”等不同来源列名映射为统一内部字段。
3. **可审计的数据导入**：支持 Excel 部分工作表与多个 CSV，确定性地完成清洗、去重、事务写入，并记录字段映射、质量摘要和缺失表。

字段映射有一个重要安全规则：只有一个标准字段能匹配时才自动映射；如果一个源列可能对应多个字段，系统会停止自动选择并要求用户确认。这避免了“看起来能导入、实际字段对应错了”的隐蔽数据问题。

### 本阶段可回答的面试问题

**Q：如何保证自动字段映射不会误匹配？**

**参考答案：** 我先对源列名做标准化，例如去掉空格、下划线和连字符并统一小写，再与每张表的中英文别名比对。但系统只接受唯一候选；存在多个候选时会返回歧义列表，由用户确认。项目还专门写了回归测试，覆盖列名标准化与歧义列不自动映射两类风险。

## 7. 面试表达小技巧

- 先讲业务价值，再讲技术：不要只说“用了 LangGraph”，要说它如何把复杂分析拆成可控流程。
- 说明边界：真实平台 API 适配器已预留，但 MVP 先采用文件导入，避免未经授权的数据接入。
- 诚实说明取舍：项目使用单体架构以便个人完成和部署；未来可按数据源、计算任务扩展。
- 准备一个完整案例：例如“最近 30 天销售下降原因”，从数据质量、SQL、渠道/商品拆解、异常、建议依次讲清楚。
